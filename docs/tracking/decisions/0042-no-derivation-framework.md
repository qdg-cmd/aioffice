# 0042 — 문서 만들기의 변환 짝을 하나의 틀로 묶지 않는다

## 맥락

껍데기 앱의 만들기 창은 한 문서로 다른 문서를 만든다. 지금 앱이 직접 하는 변환은 세 짝뿐이다. 지도 → 마크다운, 지도 → 슬라이드, 마크다운 → 지도(`apps/shell/src/main/generate/convert.ts`의 `convertSource`). 나머지는 대상 편집기의 AI에게 넘긴다.

짝이 늘면 코드가 문서 종류의 곱으로 늘어날 것을 걱정해, 모든 문서를 공통 개요 나무로 읽고 재료·의도·대상·관계 네 축을 등록으로 조합하는 패키지 `@genoffice/derive`를 만들어 보았다(2026-10-17, 로컬 브랜치 `wip/derive`, 커밋 `ac53e8fc`). 코어와 시험까지 썼고, 앱에는 붙이지 않았다.

## 결정

**변환 짝을 묶는 틀을 만들지 않는다.** 짝은 세 개이고 늘어날 계획도 없다. 세 짝을 위해 네 축짜리 등록 모델, 계보 저장소, 세션 객체를 들이는 것은 실제 코드보다 틀이 더 크다. 짝은 지금처럼 `convertSource`의 갈래로 둔다.

`wip/derive` 브랜치와 `packages/derive`는 지웠다(2026-10-20). 원격에 올린 적이 없어 코드는 남아 있지 않다.

## 택하지 않은 것

- **`@genoffice/derive`를 앱에 붙이기.** 만들기 창(`GenerateSession`)과 `convertSource`를 다시 짜야 하는데, 얻는 것은 세 짝의 정리뿐이다. "고치는 범위는 필요한 만큼" 원칙에 어긋난다.
- **패키지만 남겨 두기.** 쓰는 곳 없는 패키지는 검사·의존성 관리 비용만 든다. 다른 세션이 다시 꺼내 이어 붙일 빌미도 된다.

## 결과

- 만들기 창의 동작과 코드는 바뀌지 않는다.
- 만든 문서의 출처는 지금처럼 결정 0018의 `document-links.json`에 적는다.
- 앱이 직접 하는 변환 짝이 여럿 늘어 같은 코드가 되풀이되기 시작하면 이 결정을 다시 본다. 그때는 이 결정을 대체하는 기록을 쓴다.
