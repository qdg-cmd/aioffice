# project-store

## 맡은 범위

문서별 AI 대화 기록과 "프로젝트"(파일 묶음)를 사용자 PC에 저장한다. `<userData>/projects/` 아래의 `index.json`, `<projectId>/project.json`, `<projectId>/chats/<chatId>.jsonl`을 읽고 쓴다. 렌더러와 메인이 함께 쓰는 IPC 계약 타입(`ProjectApi`)도 여기서 정의한다. Docs·Sheets·Slides 메인 프로세스가 `ProjectStore`를 만들어 쓰고, HTML·Markdown을 포함한 다섯 편집기의 preload와 렌더러는 타입만 가져간다.

## 맡지 않는 것 (경계)

- IPC 핸들러 등록과 userData 경로 결정은 각 앱의 메인 프로세스가 한다. 이 패키지는 Electron을 import하지 않고 경로를 생성자 인자로 받는다.
- 문서 파일 자체는 건드리지 않는다. 경로를 키로 쓸 뿐이다.
- 모델에 보낼 대화 구성과 도구 실행은 `packages/agent-core`와 각 앱의 AI 코드다. 여기는 기록을 남기고 되읽는 데서 끝난다.

## 항상 지켜야 하는 것

- `projectId`와 `chatId`는 `^[A-Za-z0-9_-]+$`만 받는다. 파일 경로를 만들기 전에 검사하고, 어긋나면 삼키지 않고 던진다. 새 공개 메서드도 파일에 닿기 전에 같은 검사를 거친다.
- 파일 경로의 키는 `canonicalPathKey` 하나다(`realpathSync.native` 결과를 NFC로). 심볼릭 링크와 Windows의 대소문자·짧은 이름 변형이 같은 대화로 모여야 한다. 맵을 조회할 때는 `findMapKey`를 거쳐 예전 표기로 저장된 항목까지 찾고, 찾으면 정식 키로 옮긴다. 받은 경로 문자열로 `fileMap`을 직접 조회하지 않는다.
- `chatId`는 한 번 등록되면 파일 이름이 바뀌어도 그대로다. `fileRenamed`는 맵의 키만 옮긴다. 대화 파일을 새 경로의 해시로 다시 이름 짓지 않는다.
- 대화 파일을 덮어쓰지 않는다. 대상이 이미 있으면 `seq`를 이어 매겨 뒤에 붙인다(`renameOrMergeChat`). 프로젝트 삭제와 이름 바꾸기로 밀려난 대화는 지우지 않고 `projects/.trash/`로 옮긴다.
- JSON은 임시 파일에 쓴 뒤 rename한다. JSONL 읽기는 줄 단위로 관대하다. 깨진 줄과 `seq`가 유한수가 아닌 줄은 건너뛰고 나머지를 돌려준다.
- 저장 크기에 상한을 둔다. 본문은 32,000자에서 자르고 `[truncated]`를 붙인다. 되풀이에 빠진 모델이 한 번에 내놓은 수 MB가 JSONL 한 줄이 되고, 다시 열 때 모델 입력으로 되돌아가는 것을 막는 값이다. 도구 입출력 필드는 16,000자, 메시지당 도구 64개와 첨부 32개, 프로젝트 이름은 128자다.
- 읽기에도 상한을 둔다. `loadChat`은 기본 200건, 최대 10,000건이고 파일의 끝 8 MiB만 읽는다. 한 레코드가 그보다 크면 64 MiB까지 뒤로 넓히고, 그래도 줄 경계를 못 찾으면 빈 대화로 연다.
- 사용자 메시지의 스킬 칩(`skills`, `ChatSkillChip`)은 식별자·출처·제목만 저장한다. 스킬 글은 저장하지 않는다(다시 보낼 때 지금 내용을 다시 읽는다). 메시지당 32개, 식별자 512자, 출처·제목 200자이고 모양이 틀린 칩은 버린다.
- `default` 프로젝트는 이름 변경과 삭제를 거부한다. 읽히지 않는 `default/project.json`은 새 내용으로 덮지 않고 `.corrupt-<시각>` 이름으로 옮겨 둔다.

## 이 모듈의 방식

- 첫 assistant 메시지가 오기 전의 메시지는 디스크에 쓰지 않고 메모리에 둔다. 중단되거나 실패한 요청이 사용자 메시지 하나만 든 파일을 남기지 않게 하려는 것이다. 버퍼가 200건(`MAX_PENDING_OPENING_MESSAGES`)에 닿으면 버리지 않고 파일을 일찍 만든다. `loadChat`은 이 버퍼를 합쳐서 돌려주고, 대화를 옮기거나 합치기 전에는 양쪽 버퍼를 먼저 내려쓴다.
- `seq`는 저장소가 매긴다. 처음 한 번 파일에서 최대값을 읽고 그 뒤로는 인스턴스의 메모리 카운터를 쓴다.
- `appendChatMessage`는 쓰기에 실패하면 경고를 남기고 다시 던진다. 파일 머리의 설계 주석은 "던지지 않는다"고 적고 있지만 현재 동작은 던지는 쪽이다. 버퍼 내려쓰기, 휴지통 이동, 대화 파일 이름 바꾸기의 실패는 경고만 남긴다.
- 경로에 등록된 대화 id가 없으면 정식 키의 SHA-256 앞 16자를 쓴다. 다만 예전 버전이 원시 경로의 해시로 써 둔 파일이 있으면 그것을 따른다.
- `listProjectFiles`는 지금 디스크에 있는 파일만 돌려준다. `project.json`의 `files`는 지난 기록이라 사라진 경로가 남아 있을 수 있다. `ChatMeta.approxCount`는 파일 크기를 120바이트로 나눈 추정값이다.

## 테스트

- `npm run test -w @genoffice/project-store`, 또는 패키지 폴더에서 `npx vitest run`. 테스트마다 `os.tmpdir()` 아래에 임시 저장소를 만든다. 픽스처 파일은 없다.
- 심볼릭 링크 테스트는 링크를 만들 수 있는 환경에서만 돌고, 대소문자 변형 테스트는 Windows에서만 돈다.
- `tests/store.test.ts`의 `deleteProject > files of a deleted project revert to default`는 Windows에서 변경 이전부터 실패하는 것으로 알려져 있다. 테스트가 `/test/file.docx`라는 POSIX 경로가 `fileMap`의 키로 그대로 남기를 기대하는데, Windows에서는 `/test`가 현재 드라이브의 폴더로 풀리고 그 폴더가 실제로 있으면 키가 `<드라이브>:\test\file.docx`로 저장된다.
- 경로 키 로직을 바꾸면 예전 표기 조회, 이름 바꾸기, 합치기 경로를 덮는다. 상한을 바꾸면 경계값을 넣는다. 테스트에서 경로를 맵 키와 비교할 때는 `canonicalPathKey`를 거친 값을 쓴다.
