# zip-gate

## 맡은 범위

zip 압축 폭탄을 막는 공용 관문이다. 메모리에 올라온 zip 바이트를 받아, 어떤 파트도 자기가 선언한 크기보다 크게 풀리지 않는지 직접 확인하고 한도를 넘으면 던진다. `packages/docx-engine`, `packages/pptx-engine`, `packages/xlsx-gateway`가 문서를 여는 첫 단계에서 부르고, `packages/file-parse`는 docx-engine이 다시 내보낸 같은 함수를 쓴다.

## 맡지 않는 것 (경계)

- zip에서 내용을 꺼내는 일은 하지 않는다. 호출하는 엔진이 각자의 zip 리더로 한다.
- 형식별 한도 값은 호출자가 정한다. 여기에는 기본값만 있고, `pptx-engine`과 `xlsx-gateway`는 자기 상수를 넘긴다.
- Rust 사이드카(`apps/sheets/native/xlsx-engine`)는 같은 규칙을 자체 구현으로 갖는다. 이 패키지를 고쳐도 그쪽은 바뀌지 않는다.

## 항상 지켜야 하는 것

- `src/`에서 Node 내장 모듈과 jszip을 import하지 않는다. 이 코드는 렌더러 번들에 그대로 들어가고, `node:*` import는 Vite의 브라우저용 대체 모듈에서 빌드를 깨뜨린다. jszip은 테스트 전용 devDependency로만 둔다.
- 중앙 디렉터리가 선언한 크기를 믿지 않는다. `assertZipInflatesWithinLimits`는 파트를 스트림으로 풀다가 선언값을 넘는 순간 취소하므로, 거짓 선언은 실제 내용 크기가 아니라 선언값 + 1바이트 지점에서 잡힌다. 선언 크기만 보는 `assertDeclaredSizesWithinLimits`는 값싼 사전 검사일 뿐이다. 이것만으로 열기를 허용하지 않는다.
- 합계 한도는 선언값이 아니라 실제로 확인한 길이를 더해서 판정한다.
- 기본 한도 `DEFAULT_ZIP_LIMITS`는 파트 10,000개, 파트당 512 MiB, 합계 1.5 GiB다. 엔진들이 이 값을 공유한다는 것을 테스트가 고정하고 있다.
- 다룰 수 없는 형태는 통과시키지 않고 던진다. zip64, 암호화 항목, 저장(0)과 deflate(8) 밖의 압축 방식, 파일 범위를 벗어나는 오프셋이 그렇다.
- 한도 위반과 거짓 선언의 오류는 `zip rejected:`로 시작한다. 풀기 도중의 예외를 다시 포장할지 가르는 표지로도 쓰이므로 이 접두를 바꾸지 않는다. 구조가 깨진 경우는 `zip:`으로 시작한다.

## 이 모듈의 방식

- 중앙 디렉터리에서 필요한 다섯 필드만 읽고, 모든 오프셋을 건드리기 전에 파일 길이와 대조한다. 데이터 시작 위치는 로컬 헤더의 길이 필드로 다시 계산한다. 중앙 디렉터리의 사본과 다를 수 있다.
- 저장 방식 파트는 풀지 않고 길이만 비교한다. 실제 문서의 그림이 대부분 여기에 해당해서 정상 파일에는 비용이 거의 들지 않는다.
- 선언보다 적게 풀리는 파트는 거부하지 않는다. 막는 것은 선언보다 많이 나오는 쪽이다.
- 디렉터리 항목은 파트 수에 넣지 않는다.
- `streamBytes`는 `new Blob([bytes]).stream()`을 대신한다. 앱 테스트가 도는 jsdom의 `Blob`에는 `stream()`이 없다. 입력을 64 KiB씩 잘라 넣기 때문에 중간에 취소할 수 있다. `docx-engine`의 gzip 메타파일 해제도 이 함수를 쓴다.

## 테스트

- `npm run test -w @genoffice/zip-gate`, 또는 패키지 폴더에서 `npx vitest run`. 픽스처 파일은 없다. JSZip으로 만든 zip의 중앙 디렉터리에서 선언 크기를 고쳐 써서 거짓말하는 파일을 만든다.
- 판정을 바꾸면 "거짓 선언이 선언값 근처에서 잡힌다"와 "정직한 파일은 통과한다"를 둘 다 넣는다. 한도는 테스트용 작은 값을 넘겨서 확인한다.
- Windows에서 원본 코드 그대로도 실패하는 테스트는 없다.
